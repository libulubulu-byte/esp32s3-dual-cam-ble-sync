3 · Sync acceptance (batch)

For every FIRE,<lead_ms> the host pushes an absolute trigger instant to the slave (ARM,<T_slave>); each board then fires from its own esp_timer. The next shot is armed only after both boards report FIRE_ACTUAL, so the spacing stays exact.

Interval is the minimum spacing between two consecutive shots (measured from the moment FIRE is sent). It must be larger than Lead plus the round-trip log time, otherwise the batch is re-based.

4 · Results (the µs column is the evidence)

Δ = host_fire − slave_fire and sync_error = |Δ − median(Δ)|, both taken from the esp_timer reading captured inside the device at the moment of firing.
★ Δ itself carries the difference between the two boards' power-on instants (each esp_timer counts from 0, so they can differ by seconds), therefore Δ must not be read as the sync error. median(Δ) is that fixed clock difference; only the fluctuation left after removing it is the physical sync error.
⚠ Only the sync_error column is judged, sample by sample, against Limit (µs).
Reference columns (never used for acceptance): jitter H/jitter S are each board's own t_fire − target, i.e. single-board timer precision (20–40 µs in practice) — a small value does not mean the two boards agreed on an instant. |Δj| is the difference between the two boards' timer precisions.
This page never uses "when the notification arrived here" for any judgement — that number is entirely the BLE connection interval (15 ms) plus browser JS scheduling, and says nothing about device precision.

What each column means (the whole chain: host_fire / slave_fire → Δ → subtract the fixed clock offset → sync_error ← the only column that decides PASS/FAIL)

  • # — sample id, run-index (e.g. 1-03 = run 1, shot 3). A timed-out row is red and reads timeout (HOST MISS / SLAVE ok).
  • host_fire (µs) — the host's esp_timer_get_time() captured at the instant it fired. Local clock, counts from 0 at power-on.
  • slave_fire (µs) — the same for the slave, relayed over BLE. ★ A different clock: its origin can be seconds away from the host's.
  • Δ (µs) — host_fire − slave_fire. ★ This is NOT the sync error: it still contains the fixed difference between the two power-on instants, so it legitimately reads hundreds of thousands of µs. Orange = positive, blue = negative.
  • jitter H — the host's own timer error (actual − scheduled). Purely single-board esp_timer precision (20–40 µs in practice); a small value does not mean the two boards agreed on an instant.
  • jitter S — the same for the slave.
  • |Δj| — |jitter H − jitter S|, i.e. how different the two boards' timer precisions are.
  • sync_error (µs) — |Δ − median(Δ)|. Subtracting median(Δ) removes that fixed clock offset, and whatever fluctuation is left is the real physical sync error. ⚠ The only column used for the verdict, compared per sample against Limit (µs). Green = within limit, red = over.

5 · Acceptance criteria (what this page actually judges)

    
All of the following must hold for a PASS:

    
    
      
  • Complete: samples == runs × shots per run
    • 
      
  • No timeout: every sample must receive both
          HOST,FIRE_ACTUAL and SLAVE,FIRE_ACTUAL
          (a timed-out sample is counted separately and fails the batch immediately)
    • 
      
  • Per sample: |sync_error| ≤ Limit (µs)
          (150 µs by default)
    • 
    

    

      Project targets for reference: mean < 100 µs, max < 150 µs.
      Measured so far: mean ≈ 3–4 µs / max ≈ 5–70 µs,
      a margin of 20× or better.
